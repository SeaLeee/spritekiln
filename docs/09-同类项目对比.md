# 同类项目对比

对比对象（均为 2026-10 左右的状态）：

- [RosemyneH/pixel-art-factory](https://github.com/RosemyneH/pixel-art-factory) — MIT，首版 2026-09
- [0x0funky/agent-sprite-forge](https://github.com/0x0funky/agent-sprite-forge) — MIT，v0.4.0（10-06），约 4.5k stars
- [aldegad/sprite-gen](https://github.com/aldegad/sprite-gen) — 约 3k stars
- [MubarakHAlketbi/game-asset-mcp](https://github.com/MubarakHAlketbi/game-asset-mcp) — MCP server

> Star 数与版本会变化；下表按上述时间点的公开信息整理。四个项目的内部实现细节以其 README 为准，本文不做超出公开描述的推断。

---

## 1. 一句话结论

- **pixel-art-factory**：本地 SDXL + 像素 LoRA 的「批量出图 + 打包」流水线，偏素材工厂。
- **agent-sprite-forge**：一张主静帧 → 整套动作精灵，强在动作管线与引擎导出，媒体生成走外部 API。
- **sprite-gen**：一张底图 → 可用的 sprite atlas / 透明循环动画，强在「已有底图之后」。
- **game-asset-mcp**：MCP 形态的程序化像素/瓦片/3D 生成，强在确定性与工具接入，风格上限较低。
- **SpriteKiln**：本地优先的**全流程工作台**——网页画布 + Skill/CLI + MCP + 内置 Agent 共用 26 个能力，覆盖像素/高清/角色/UI/地图/动画/3D/策划，引擎导出与批量产出齐备。

不是谁替代谁：前四个更像「一个很深的工具」，SpriteKiln 更像「把很多工具装进同一个工作台」。

## 3. 逐个看差异

### 3.1 pixel-art-factory

**它做得好的地方**：把「像素素材」当成一条可批量的生产线——预设固定尺寸与数量、调色板量化、透明裁切、spritesheet 打包、Phaser atlas、JSON manifest 整包批量，还有 MCP 接入。这是典型的「素材工厂」思路。

**和 SpriteKiln 的差别**：

- 它绑定 SDXL + 像素 LoRA，风格与模型强相关；SpriteKiln 把生图抽象成 Provider，可以换 ComfyUI 工作流、云端模型或离线引擎。
- 它偏 2D 像素素材；SpriteKiln 还有高清、角色多视图、UI、地图、动画、3D 与策划文档。
- 它没有网页画布与内置 Agent；SpriteKiln 的每种能力都能在画布上被用户接管。

**我们汲取的**：JSON manifest 批量。已实现为 `kiln_api.py batch`，支持 `output_dir`、`stop_on_error`、逐项报告与 `batch_report.json`；示例见 `examples/pack.example.json`。

### 3.2 agent-sprite-forge

**它做得好的地方**：从一张主静帧出发，用图生视频产出整套动作，并且把「门控重拍 + soft matte 去背 + 配准 + 循环 + 重定时 + 色锁」串成了工程管线；导出覆盖 Godot / Tiled / LDtk / Aseprite / Web，还能生成分层地图。这是目前最接近「动作精灵量产」的开源方案之一。

**和 SpriteKiln 的差别**：

- 它的媒体生成主要走外部 API，本机不跑扩散模型；SpriteKiln 默认本地 ComfyUI，云端只是可选项。
- 它的强项集中在「动作」；SpriteKiln 的动作只是 26 个能力中的 3 个，前后还有角色定稿、地图、UI、3D。
- 它的门控包含视觉/语义判断；SpriteKiln 的质量门控是**纯几何的确定性检查**（见下），不调用第二个模型。

**我们汲取的**：

1. **质量门控 + 重拍**：`backend/app/pixel/qa.py`，在 `animate` 里接入 `quality_gate`（off/standard/strict）与 `retakes`。检查空帧、主体面积波动、尺寸漂移、重复帧；中心漂移只报告不判失败（跳跃/攻击本来就该移动）。
2. **绝对帧矩形**：`sheet.json` 直接写每帧的 `x/y/w/h`、`duration_ms`、`pivot`，不再让引擎自己算行列。
3. **引擎旁挂元数据**：动画目录里同时写 `aseprite.json` 与 `phaser.json`，ZIP 导出也会带上。
4. **Tiled 导出**：`tileset_gen` 的产物在 ZIP 里附带 `.tsj`，双网格瓦片带四角掩码属性。

**没有照搬的**：LDtk 导出、分层地图、基于视觉模型的重拍判定。前两者需要额外的 schema 与数据模型；后者会引入第二个模型和误判成本，与「假警告比不报更坏」的原则冲突。

### 3.3 sprite-gen

**它做得好的地方**：目标非常聚焦——给定一张底图，产出游戏可用的 sprite atlas 与透明循环动画。对「已经有角色定稿、只差动画」的团队很顺手。

**和 SpriteKiln 的差别**：它要求你先有底图；SpriteKiln 可以从提示词开始，也可以接底图，还能继续做 3D 与引擎导出。反过来说，如果你的需求就是「底图 → 动画」，它的路径更短、心智更小。

**我们汲取的**：帧级检查与「循环最后回到首帧」的约束；SpriteKiln 的 `animate` 在循环时会多请求一帧并丢弃尾帧，质量门控会检查重复帧。

### 3.4 game-asset-mcp

**它做得好的地方**：MCP 原生、确定性 palette / matrix 像素、tile、OBJ/GLB，适合让 Agent 稳定地生成「规格明确」的素材；不依赖 GPU，也不会有模型随机性。

**和 SpriteKiln 的差别**：它偏程序化，风格上限低；SpriteKiln 用生成模型追求更高的美术上限，同时保留 `mock` / `procedural` 作为确定性兜底。两者其实可以互补：程序化出结构，生成模型出风格。

**我们汲取的**：MCP 工具的参数 schema 要显式、可描述；SpriteKiln 的 MCP 会把能力参数完整暴露给 Agent，并要求先 `describe_capability` 再运行。

## 4. SpriteKiln 的独特组合

单看某一项，前四个项目都有更深的点；SpriteKiln 的差异在**组合**：

1. **同一套能力目录**同时服务网页、Skill、CLI、MCP、内置 Agent——用户在画布上手动做的，和 Agent 自动做的是同一件事。
2. **本地优先 + 云端兜底 + 离线兜底**的三级路由，任何一环坏掉都不会让流水线停摆。
3. **从 2D 到 3D 再回到 2D**：单图 → GLB → 多方向渲染 → 方向精灵，解决「8 方向一致性」这个生成模型很难直接做好的问题。
4. **产物即工程文件**：动画不只给 GIF，还给 SpriteFrames、Aseprite、Phaser、Tiled 元数据。
5. **确定性质量门控**：不引入第二个模型，阈值可解释，误报可控。

## 5. 验证记录

本次汲取的功能都有离线测试（不依赖 GPU、网络或真实模型）：

```text
python -m pytest backend/tests -q
23 passed
```

覆盖点：

- `test_quality_gate_passes_real_motion_and_rejects_empty_or_frozen`：真实动作通过；空帧/冻结帧被拒；
- `test_engine_export_uses_absolute_frame_rects`：Aseprite 帧矩形、frameTags、Phaser 动画名；
- `test_tiled_tileset_json_for_dual_grid`：`.tsj` 的 tilecount/columns/image/角掩码；
- `test_capabilities_offline[animate]`：动画任务走 mock/procedural 全链路，断言 `meta.qa.ok` 与 `aseprite/phaser` 文件；
- `test_capabilities_offline[tileset_gen]`：ZIP 内含 `.tsj`；
- `test_discovers_current_codex_provider`：只读 cc-switch DB 拿到 provider/model/端口，输出里不含 Key；
- `test_comfyui_model_overrides_keep_defaults_when_empty`：生图/视频模型文件名可换，留空仍用工作流默认；
- `test_chat_stream_with_rules_emits_plan_and_done`：流式规划的事件顺序（start → … → plan → done）与消息落库；
- `test_parse_sse_line_reads_reasoning_and_content`：OpenAI 兼容流的 reasoning/content 分片解析（含忽略代理返回的非流式整包）。

这些测试验证的是**格式与判定逻辑**，不是「在 Godot/Tiled/Phaser 里实际播放正确」。导出仍属于解析级验证，和 agent-sprite-forge 0.4.0 的 Godot/LDtk 导出处于同一诚实级别。欢迎用真实引擎跑通后提 issue/PR 补运行级验证。

## 6. 怎么选

- 只要像素素材批量出图，且接受 SDXL 工作流 → **pixel-art-factory**
- 已有一张主静帧，要一整套动作并导出多引擎 → **agent-sprite-forge**
- 已有底图，只要 atlas/循环动画 → **sprite-gen**
- 想让 Agent 稳定生成规格化像素/tile/3D，不要 GPU → **game-asset-mcp**
- 想要一个能手动接管、能接本地模型、覆盖 2D/3D、还能被 Agent 调用的工作台 → **SpriteKiln**

## 7. 已知不足（诚实清单）

- 没有 LDtk 导出、没有分层地图；
- 引擎导出未做运行级验证；
- 单用户、无认证，公网商用需二次开发（见 [08](08-开源自托管与商用部署.md)）；
- 本地 H3 动画与 Pixal3D 对显存要求高，首次配置成本不低；
- 项目较新，生态与示例还不如前四个成熟。
